**Findings that change the plan**

1. **The money shot needs a setting.** As shipped, the refusal is hidden behind "1 reply". Either set `CollapsedThreads` to `disabled` for the demo, or open the thread on camera. Each pull also makes the bot post a greeting such as `Hello! I'm ready — just tag @treasury when you need me.`, which will be on screen.
2. **The ejection does not show in Mattermost.** After removal, `treasury` stays in the Mattermost channel member list, still there about 25 minutes later and across a stack restart, and no removal line is posted. The Switch roster is correct and the boundary holds: `send_targeted_message` returns HTTP 400 `Targets not in room: treasury. Room participants: clerk, courier, reader.`, and `@treasury` draws a `switch-admin` notice that it won't reach the agent. The courier has to announce the ejection itself. This contradicts the `remove_agent_from_room` docstring, which says the agent leaves any bridged channel.
3. **Admitting `reader` to the courier lets `reader` eject the courier.** Any rule that admits `reader`, including one scoped to a single room and to `reader` alone, gave HTTP 200 on `remove_agent_from_room`. Under the default policy it is HTTP 403. Attack 5 therefore must not rely on admitting `reader`. It doesn't need to: at the default policy, prose addressed to the courier still reaches it on `filter=all` with `addressed: false`, and Switch posts its refusal as the courier.
4. **The courier's watch has a blind spot.** `reader` can call `create_room` with `treasury` in it (HTTP 200). The courier gets no `room_join`, because it isn't a member, and `treasury` gets no control frame. The refusal still holds there, so no money moves. The courier can see the room through `list_all_rooms` and remove `treasury` from outside it (HTTP 200), so it needs to poll if this attack matters. The agent-run template version is refused outright: HTTP 400 `Nothing was created: the kickoff mentions treasury, and it does not accept messages from reader... (kickoff_ignored)`.
5. **Repeated refusals turn into HTTP 429.** After 8 identical refusals, the 9th returns 429, `Retry-After: 60`, `{"detail": "This request was refused repeatedly and is not retried for 60 s. Retrying it unchanged will be refused again."}`. It counts per caller, method and path, and `post_message` still worked. A replay command that repeats an attack must not read this as a different outcome.
6. **`room_join` is not what the docs say.** The docs say agents not opted in don't receive it. At runtime, on `filter=all` it arrives anyway with `listening: false`. On `filter=addressed` it arrives only when opted in. A member can turn another agent's opt-in off: `reader` did so with `update_room` on `ap-intake` (HTTP 200). A re-invite also clears it. So the courier should stay on `filter=all` and ignore the `listening` field.
7. **"Can manage agents" does not need the server flag.** With `treasury` owner-only, the courier's removal gets HTTP 403. After `PUT /gateway/agents/{id}/can-manage-agents` with `agent_management` off, it gets HTTP 200. The brief says the flag is required. The default policy is simpler and needs neither.
8. **#1158 is real but avoidable.** A kickoff turn's activity report fails with `Invalid RootId parameter` and draws no card, while a control turn from a top-level message draws `**Worked for 6s.**`. The retries doubled from seconds up to 5 minutes apart, and they did not stop by themselves during the run. A stack stop and start cleared them: none in the following 13 minutes, which covers when the next one was due. Separately, an answer threaded under the kickoff message returned HTTP 200 with an event id and **never reached Mattermost**, though `read_context` has it. An answer at the channel root posts normally. A client that reports no activity and doesn't thread under a kickoff doesn't hit either.
9. **Other details for the architect:**
   - A kickoff arrives with `sender: @switch-admin` and `sender_name: clerk`, so don't identify people from `sender` alone on these messages.
   - A `users` rule takes the person's identity id from `list_participants`, not their Switch user id. With the Switch user id, the named person was refused. With the identity id, that person passed, others were refused, and the room scope held.
   - Claims need no proof and aren't exclusive. `clerk` claimed the controller's Mattermost account (HTTP 200, both listed), and `treasury` still refused `clerk`'s own account. Only an admin can claim for someone else (others get HTTP 403), so keep admin credentials away from the desk.
   - The seeded Mattermost accounts `admin` and `user` are added to every bridged channel, including the private `ap-release`. `clerk` gets 404 and 403 there.
   - `list_all_rooms` shows a non-member the private room's name, description and id. `get_room_detail`, `read_context`, `connect_to_room`, `update_room`, posting and removal are all refused for that non-member.
   - `treasury` on `filter=addressed` receives nothing from the hostile messages and still receives its owner's. On `filter=all` it receives the hostile text with `addressed: false`.
   - Four unaddressed messages did not arrive in a room the agent had just joined for the first time. The cause is unknown, and it did not recur in re-invite rounds. All 11 addressed owner messages arrived, the first sent 0.1 s after the room was created. A courier reading packets from room chatter should backfill with `read_context`.
